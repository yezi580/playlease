1. 系统架构与部署架构

1.1 系统架构图

整体为「双 SPA 前端 + 单体 Node 服务（蓝绿双容器）+ MySQL/Redis + 4 个三方服务」的架构，无微服务、无 MQ。

架构要点：

  • 鉴权：JWT（HS256）+ Redis 服务端会话双轨。Token 经 httpOnly Cookie（auth_token）传递，每次请求校验 Redis 会话，支持改密 / 封禁 / 角色变更即时吊销；管理员与客服的高危操作叠加 Passkey（WebAuthn）二次校验（428 STEP_UP_REQUIRED 协议）。
  • 支付安全边界：订单置为已支付只由支付回调 / 主动查单驱动，不暴露任何「确认支付」HTTP 路由；回调只信任渠道侧 RSA 验签解析出的数据，且做金额一致性校验。
  • 可靠性替代 MQ：无消息队列。跨系统异步一致（退款到账、打款到账、订单收口）依赖「DB 状态机 + reason/remark 幂等键 + 120s 资金对账定时任务 + 汇付查单」实现最终一致（见 4.6）。
  • 多实例一致性：蓝绿双容器并存期间，定时任务用 Redis 分布式锁保证同轮只跑一次；限流计数走 Redis 共享。

1.3 蓝绿发布与回滚

发布/回滚由 deploy/scripts/blue-green-deploy.sh（子命令 deploy / switch / status）驱动：

flowchart TB S(["blue-green-deploy.sh deploy"]) --> J{"读取 upstream-backend.conf<br/>判断当前活跃色"} J -->|"blue 活跃"| B1["构建镜像 my-app-api:current"] J -->|"green 活跃"| B1 B1 --> B2["只重建闲置色容器<br/>（活跃色流量全程不动）"] B2 --> B3{"轮询 healthcheck<br/>≤240s 变 healthy?"} B3 -->|"否"| ABRT["自动中止<br/>线上流量不受影响"] B3 -->|"是"| B4["原地重写 upstream-backend.conf<br/>交换 down 标记（必须保 inode：<br/>bind-mount 下 sed -i/rm+cp 会使容器读不到新内容）"] B4 --> B5{"nginx -t 校验"} B5 -->|"失败"| RB["自动回滚配置文件"] B5 -->|"通过"| B6["nginx -s reload 平滑切流<br/>3s 后确认 nginx 存活"] B6 --> B7["旧色保持运行 = 热备 + 回滚目标"] B7 --> SW(["switch 子命令 = 一键回切，不构建"])

要点：

  • 切换原子性在 nginx 配置层完成，应用零停机；worker_shutdown_timeout 30s 保证 reload 后旧 worker 最多存活 30s，避免 socket.io 长连接把旧 worker 无限留住。
  • 部署脚本对 nginx 配置采用「保 inode 的原地重写」（cat > 覆盖而非替换文件），这是 bind-mount 场景的硬约束。

4. 数据库设计

4.1 总览

数据库 game_rental，共 37 张表，InnoDB / utf8mb4_unicode_ci。所有金额字段以「分」为单位的 BIGINT 存储（序列化层输出元）。商品/订单大量使用快照字段（卖家名、标题、租金、物品单价），保证历史可追溯。

4.6 中间件说明（为什么没有 MQ）

系统未引入 RabbitMQ / Kafka。跨系统（汇付）异步结果驱动的最终一致性由以下机制等效实现：

常规 MQ 方案本系统等效实现
支付成功消息汇付异步回调（验签入账）+ 前端回站轮询触发主动查单 + 60s 超时任务兜底查单
退款/打款结果消息120s 资金对账任务（reconcileProcessingFundsOrders）扫「资金在途」场景订单，逐单调汇付退款查单/打款查单推进状态；客服亦可手动触发「同步资金结果」
延迟队列（订单超时关闭）60s 轮询扫描 + 状态条件 UPDATE（WHERE status IN (...) 防并发），关单前强制先查单防误杀
幂等消费业务幂等键：退款按 payment_refunds.reason、打款按 settlement_payouts.remark 唯一防重发；订单状态流转全部带 WHERE 守卫
死信/人工干预查单失败留痕（provider_query_status='failed'、support_note「请人工核对资金状态」），客服工作台可见

代价与取舍：轮询有秒级延迟（对账 120s），但资金类操作低频（日均订单量级小），轮询 + 幂等 + 对账在当前容量下最简可靠；若订单量上两个数量级，优先引入延迟队列与退款/打款结果 webhook 的独立消费。

事件payload说明

事件目标说明

7.3 外呼流量与回源

  • COS 生产启用内网回源（cos-internal 同地域），媒体流量不经公网出口；签名 URL 采用「时间窗口对齐」生成（同一文件在窗口期内 URL 稳定，浏览器可缓存，窗口 24h / TTL 48h）。
  • 短信、验证码、汇付调用均为低频；汇付退款/打款存在秒级异步延迟，由对账任务消化。

8.2 业务安全

支付与资金（最高优先级）：

风险防护
伪造支付回调白嫖只信任渠道侧 RSA-SHA256 验签解析出的数据，解析为空一律拒绝；回调金额 ≠ 流水金额直接拒绝
免费下单漏洞不存在任何「确认支付」HTTP 路由；订单置 paid 必须存在渠道侧 status='paid' 流水，仅回调/查单两条内部路径驱动
并发重复入账状态守卫 UPDATE ... WHERE status IN ('created','pending')；订单级 Redis 分布式锁；affectedRows=0 且双方 paid 视为幂等成功，否则 409
重复退款/打款幂等键：退款按 payment_refunds.reason、打款按 settlement_payouts.remark 唯一防重发；累计退款 ≤ 原支付金额
资金在途丢单120s 资金对账任务 + 客服手动「同步资金结果」双通道收口；查单失败留痕 provider_query_status='failed' 供人工核对
平台账户余额被划空汇付商户控台自动结算保持关闭（硬约束）；取现风控：单笔 ≤5 万、每日 5 笔
结算金额泄漏结算预览接口按角色过滤金额字段（买家只见自己的退款、卖家只见自己的入账、平台抽成仅客服可见）；额外物品双边价格互不可见

账户与后台：

风险防护
账号盗用JWT 短期 + Redis 服务端会话（可吊销）；改密/封禁/改角色即时吊销全部会话；空闲超时自动下线
后台爆破管理域 IP 白名单（含到期自动收紧脚本）；admin 登录短信单号日限收紧；主站 nginx 层对 /admin.html 与 /api/admin/* 整段 404（仅放行 Passkey/step-up 供客服台复用）
高危操作冒用Passkey（WebAuthn）二次校验，428 STEP_UP_REQUIRED 协议；受信任设备 30 天豁免可管理；策略级开关
短信轰炸 / 验证码爆破天御行为验证前置；发送间隔/手机号日限/IP 日限/校验错误次数锁定（Redis + DB 计数表双层）；nginx 短信专用限流 2r/s
越权访问全接口属主/参与方校验（商品本人、订单参与方、会话参与方、媒体属主策略）；写来源 Origin 校验；CORS fail-closed 白名单
聊天导流私单敏感词屏蔽表（加微信/转账/扫码付款等）；系统消息提示「私下交易可冻结资金」；客服可冻结资金处置
